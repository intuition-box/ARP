# Task 105 — Prepare `@arp-protocol/cli` 0.0.3

**Status:** verified 2026-11-10, `task-verifier` PASS at `bd20915`, post-mortem `.claude/learning/94-cli-0.0.3.md`; on `feat/105-cli-0.0.3` (not pushed). Publishing is the release checklist below.
**ADR:** `0175` (the sponsor default as a committed build setting; the registry name).
**Rules:** `workflow.md`, `code.md`, `claims.md`, `security.md`. Touches the CLI and the MCP server, not
the hook's source.

## Why

npm has 0.0.1 (published 2026-11-06 07:59 UTC, `npm view @arp-protocol/cli time`). 0.0.2 was prepared
on 2026-11-09 (`9e01db8`) and never published. Since then the line request went to version 3 (task 93)
and 4 (task 97), and each version stops the previous one from verifying
(`packages/protocol/src/sponsor/line.ts:21-31`): an installed 0.0.1 gets HTTP 401 from a sponsoring
service built from `main`. The release has to ship before, or with, the hosted sponsor.

## Deliverables

1. **0.0.3 everywhere the version lives.** `apps/cli/package.json`, `bun.lock`'s workspace entry,
   `server.json` (both fields), and the generated `packaging/claude/arp/.claude-plugin/plugin.json`,
   `packaging/claude/arp/bin/arp.js` and `packaging/gemini/arp/gemini-extension.json` (its `npx` pin).
   `.claude-plugin/marketplace.json` carries no version. The CLI reads its own version from
   `package.json`, so `arp --version` follows.
2. **The sponsor default, set at build time** (ADR `0175`). `apps/cli/package.json` `config.sponsorDefault`,
   empty today, is inlined by both builds as the default of `ARP_SPONSOR` (`apps/mcp/src/config.ts`);
   empty keeps `http://127.0.0.1:3200`. `ARP_SPONSOR` still overrides at run time. A CLI test checks the
   bundle holds the configured value and never reads `ARP_SPONSOR_DEFAULT` at run time.
3. **`mcpName`: `io.github.Wieedze/arp`**, the same string as `server.json`'s `name`. The namespace is
   the user's GitHub login, decided by the coordinating session on his delegation, 2026-11-10: he is a
   member, not an owner, of `intuition-box`, so the org namespace is not his to publish. Case is kept as
   the login has it; the registry does not fold case (ADR `0175`). **Moving to an org namespace later is a
   new registry entry**, not a rename.
4. **`apps/cli/CHANGELOG.md`**: what changed since 0.0.1, each item with its task. Shipped in the tarball
   (`files`).
5. **`arp_declare_used` takes `needs` and `with`** (FUTURE.md, task 97's gap). Same guard as `arp line`
   and the sponsor's `/line` (ADR `0166`): the shape of a program or a variable's name, with the outcome
   and reason it belongs to, **one skill per call**, and the skill's SKILL.md read from GitHub at `HEAD`
   must name it whole (`publishableNeed`). Nobody re-reads it after this planner, so every failure —
   not a skill URL, no single SKILL.md, GitHub's limit, an unreadable file — refuses the name rather than
   dropping it. `apps/mcp/src/handlers/declare-need.ts`, tested in `apps/mcp/test/declare-need.test.ts`.
   The Desktop and sponsored `arp_declare_used` takes only an `id` and no outcome, so it is unchanged.
6. **The release checklist**, below.

Also: `prepublishOnly` builds `dist/` so `npm publish` cannot ship a stale one; `docs/tasks/102` §2,
`apps/web/DEPLOY.md`, `apps/web/public/docs/mcp-tools.md` and `FUTURE.md` amended.

## Do not do in this task

- `npm publish`, `git push`, a tag, a deploy, `mcp-publisher publish`.
- Invent the sponsor's domain: the default stays the loopback until the user has the URL.
- The plugin icon in `apps/cli/scripts/packages.ts` (task 107 owns it). This task changes only the
  `Bun.build` call and the manifest's type there.
- `apps/hook/src/skill-failure.ts` (task 108).

## The steps for the user, and for the orchestrator

### Once the hosted sponsor has its URL (any time before step 3)

One line, from the repository root, then regenerate and commit:

```
npm pkg set config.sponsorDefault=https://<SPONSOR_PUBLIC_HOST> --prefix apps/cli
bun run --cwd apps/cli packages
git commit -am "chore(cli): the hosted sponsor is the default"
```

Skipped, 0.0.3 ships with the loopback and a tester sets `ARP_SPONSOR=https://<SPONSOR_PUBLIC_HOST>`.

### Max

1. `npm login` (the account that owns `@arp-protocol`). Nothing else.

### The orchestrator, after the gates below are green on the branch being released

2. From `apps/cli`: `npm publish --access public`. `prepublishOnly` rebuilds `dist/` first.
3. Check: `npm view @arp-protocol/cli@0.0.3 mcpName` prints `io.github.Wieedze/arp`.

### The MCP Registry (Max: the login is his GitHub account)

From `docs/tasks/102` §2a, with the name settled:

4. Install the publisher: `brew install mcp-publisher`, or the release archive from
   github.com/modelcontextprotocol/registry/releases.
5. From the repository root: `mcp-publisher validate`, then `mcp-publisher login github` as `Wieedze`,
   then `mcp-publisher publish`. The registry reads `mcpName` from npm at the exact version in
   `server.json` (0.0.3), so step 2 comes first.
6. Once the hosted MCP endpoint is deployed: add its `remotes` entry to `server.json`, bump `version`,
   publish again (`docs/tasks/102` §2a step 6).

The sponsoring service and the CLI update together: deploy the sponsor from the same `main` as 0.0.3.
